# TlalocAi Raspberry Agent

The Raspberry Agent is a .NET Worker Service under:

`src/Agents/TlalocAi.RaspberryAgent/TlalocAi.RaspberryAgent.Worker`

It never requires the backend or frontend to connect directly to the Raspberry by IP or port. The agent always makes outbound calls to the backend:

- Heartbeat: `POST /api/devices/{deviceId}/heartbeat`
- Telemetry: `POST /api/devices/{deviceId}/telemetry`
- Command polling: `GET /api/devices/{deviceId}/commands/pending`
- Ack: `POST /api/devices/{deviceId}/commands/{commandId}/ack`
- Reject: `POST /api/devices/{deviceId}/commands/{commandId}/reject`

The observed public IP is only diagnostic metadata stored by the backend. It is not used for command delivery.

## Publish

For Raspberry Pi OS 64-bit:

```bash
dotnet publish ./src/Agents/TlalocAi.RaspberryAgent/TlalocAi.RaspberryAgent.Worker/TlalocAi.RaspberryAgent.Worker.csproj \
  -c Release \
  -r linux-arm64 \
  --self-contained false
```

For Raspberry Pi OS 32-bit:

```bash
dotnet publish ./src/Agents/TlalocAi.RaspberryAgent/TlalocAi.RaspberryAgent.Worker/TlalocAi.RaspberryAgent.Worker.csproj \
  -c Release \
  -r linux-arm \
  --self-contained false
```

Copy the publish output to `/opt/tlalocai/raspberry-agent` and edit `appsettings.json` with the real backend URL and device API key.

## systemd

Create `/etc/systemd/system/tlalocai-raspberry-agent.service`:

```ini
[Unit]
Description=TlalocAi Raspberry Agent
After=network-online.target
Wants=network-online.target

[Service]
WorkingDirectory=/opt/tlalocai/raspberry-agent
ExecStart=/usr/bin/dotnet /opt/tlalocai/raspberry-agent/TlalocAi.RaspberryAgent.Worker.dll
Restart=always
RestartSec=5
Environment=DOTNET_ENVIRONMENT=Production

[Install]
WantedBy=multi-user.target
```

Enable it:

```bash
sudo systemctl daemon-reload
sudo systemctl enable tlalocai-raspberry-agent
sudo systemctl start tlalocai-raspberry-agent
sudo journalctl -u tlalocai-raspberry-agent -f
```

## Configuration

Default configuration lives in `appsettings.json`. It includes:

- `Agent.Mode`: `Simulation` or real mode.
- `Backend.BaseUrl`: cloud backend or gateway URL.
- `Backend.ApiKey`: device API key generated by the Devices API.
- GPIO pins for tower, cistern, flow sensor and ESP32 status inputs.
- ESP32 serial ports `/dev/ttyUSB0` and `/dev/ttyUSB1`.
- Safety options for low tower level, no-flow shutdown and unsafe-command rejection.

## GPIO and serial

Recommended Raspberry BCM map:

- Tower level sensors: GPIO5, GPIO6, GPIO13, GPIO19, GPIO26.
- Cistern level sensors: GPIO12, GPIO16, GPIO20, GPIO21, GPIO25.
- Hall flow sensor: GPIO23.
- Tower pump output: GPIO17 through a power driver.
- Cistern pump output: GPIO27 through a power driver.
- ESP32 A status inputs: GPIO4, GPIO18, GPIO22, GPIO24.
- ESP32 B status inputs: GPIO10, GPIO9, GPIO11, GPIO8.

ESP32 communication uses USB serial by default:

- ESP32 A: `/dev/ttyUSB0`
- ESP32 B: `/dev/ttyUSB1`

If UART pins are used instead of USB serial, document TX/RX wiring and common GND before deployment.

## Electrical safety

- Do not connect pumps or valves directly to GPIO.
- Use MOSFET drivers, isolated switching modules, contactors or SSR modules appropriate to the load.
- Use an external power supply for pumps and valves.
- Join Raspberry, ESP32 and actuator supply GND when using common DC switching.
- Convert any 5V sensor output to 3.3V before Raspberry or ESP32 GPIO input.
- Add flyback diodes to DC inductive loads.
- If pumps are AC, use a properly rated contactor, SSR or isolated module. Do not manipulate mains wiring without proper protection.

## Simulation mode

The default `Agent.Mode` is `Simulation`, so the worker can run without Raspberry or ESP32 hardware. The worker still uses the normal outbound flow:

- Heartbeat is sent by `AgentHeartbeatWorker`.
- Telemetry is sent by `AgentTelemetryWorker` through `IBackendClient.PublishTelemetryAsync`.
- Commands are polled and executed by `AgentCommandWorker`.
- Local safety is still enforced by `AgentTelemetryWorker.ApplyLocalSafetyAsync`, `PumpControlService`, `ValveCommandService` and `SafetyEvaluationService`.

The simulation is configured under `Simulation`:

- `Simulation.Enabled`: enables simulated GPIO, flow and ESP32 state even if `Agent.Mode` is not `Simulation`.
- `Simulation.Scenario`: `Demo`, `Safety`, `NoFlow`, `Critical` or `ValveLock`.
- `Simulation.CycleSeconds`: simulated time used for each generated plant cycle.
- `Simulation.InjectNoFlowEveryCycles`: injects a no-flow event every N cycles.
- `Simulation.InjectCriticalLevelEveryCycles`: injects tower/cistern critical or full states every N cycles.
- `Simulation.EnableNoFlowScenario`, `Simulation.EnableCriticalLevelScenario`, `Simulation.EnableCisternFullScenario`, `Simulation.EnableValveLockScenario`: enables or disables each safety scenario.

Generated telemetry includes:

- Tower and cistern levels between 0 and 5.
- Variable flow in L/min and accumulated total liters.
- Tower and cistern pump state.
- Four valve states.
- Sixteen container states.
- Warnings and faults such as `No flow detected while pump is on.`, `Tower level is critical.`, `Cistern level is critical.` and valve lock reasons.

When `Backend.BaseUrl` still contains `TU_BACKEND_EN_NUBE`, the worker uses `SimulatedBackendClient` for offline tests. When `Backend.BaseUrl` points to a real backend or Gateway, simulation publishes real HTTP telemetry using `X-Device-Api-Key`.

### Run a dummy meter against the local Gateway

1. Start the platform and frontend:

```bash
docker compose up -d --build
```

2. Open the frontend and create a dummy device from `/devices`. Use an id that matches the worker configuration, for example `dummy-meter-001`. Copy the API key returned when the device is created. The clear API key is only shown when creating the device or rotating the key.

   You can also create it through the API after logging in:

```bash
curl -X POST http://localhost:5100/api/devices \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"id":"dummy-meter-001","name":"Dummy Meter 001","description":"Simulated worker for frontend monitoring"}'
```

3. Configure `src/Agents/TlalocAi.RaspberryAgent/TlalocAi.RaspberryAgent.Worker/appsettings.Simulation.json`:

```json
{
  "Agent": {
    "DeviceId": "dummy-meter-001",
    "Mode": "Simulation"
  },
  "Backend": {
    "BaseUrl": "http://localhost:5100/",
    "ApiKey": "PASTE_DEVICE_API_KEY_HERE",
    "TelemetryIntervalSeconds": 2,
    "HeartbeatIntervalSeconds": 10
  },
  "Simulation": {
    "Enabled": true,
    "Scenario": "Demo",
    "CycleSeconds": 2,
    "InjectNoFlowEveryCycles": 8,
    "InjectCriticalLevelEveryCycles": 6
  }
}
```

4. Run the worker with the simulation environment:

PowerShell:

```powershell
$env:DOTNET_ENVIRONMENT = "Simulation"
dotnet run --project ./src/Agents/TlalocAi.RaspberryAgent/TlalocAi.RaspberryAgent.Worker/TlalocAi.RaspberryAgent.Worker.csproj
```

Bash:

```bash
DOTNET_ENVIRONMENT=Simulation dotnet run --project ./src/Agents/TlalocAi.RaspberryAgent/TlalocAi.RaspberryAgent.Worker/TlalocAi.RaspberryAgent.Worker.csproj
```

5. Open `/monitoring` in the frontend and select the dummy device. You should see changing levels, flow, pumps, valves, containers and safety alerts without physical hardware.
