# TlalocAi Raspberry Agent

The Raspberry Agent is a .NET Worker Service under:

`src/Agents/TlalocAi.RaspberryAgent/TlalocAi.RaspberryAgent.Worker`

It never requires the backend or frontend to connect directly to the Raspberry by IP or port. The agent always makes outbound calls to the backend:

- Heartbeat: `POST /api/devices/{deviceId}/heartbeat`
- Telemetry: `POST /api/devices/{deviceId}/telemetry`
- Command polling: `GET /api/devices/{deviceId}/commands/pending`
- Ack: `POST /api/devices/{deviceId}/commands/{commandId}/ack`
- Reject: `POST /api/devices/{deviceId}/commands/{commandId}/reject`

The observed public IP is only diagnostic metadata stored by the backend. It is not used for command delivery.

## Publish

For Raspberry Pi OS 64-bit:

```bash
dotnet publish ./src/Agents/TlalocAi.RaspberryAgent/TlalocAi.RaspberryAgent.Worker/TlalocAi.RaspberryAgent.Worker.csproj \
  -c Release \
  -r linux-arm64 \
  --self-contained false
```

For Raspberry Pi OS 32-bit:

```bash
dotnet publish ./src/Agents/TlalocAi.RaspberryAgent/TlalocAi.RaspberryAgent.Worker/TlalocAi.RaspberryAgent.Worker.csproj \
  -c Release \
  -r linux-arm \
  --self-contained false
```

Copy the publish output to `/opt/tlalocai/raspberry-agent` and edit `appsettings.json` with the real backend URL and device API key.

## systemd

Create `/etc/systemd/system/tlalocai-raspberry-agent.service`:

```ini
[Unit]
Description=TlalocAi Raspberry Agent
After=network-online.target
Wants=network-online.target

[Service]
WorkingDirectory=/opt/tlalocai/raspberry-agent
ExecStart=/usr/bin/dotnet /opt/tlalocai/raspberry-agent/TlalocAi.RaspberryAgent.Worker.dll
Restart=always
RestartSec=5
Environment=DOTNET_ENVIRONMENT=Production

[Install]
WantedBy=multi-user.target
```

Enable it:

```bash
sudo systemctl daemon-reload
sudo systemctl enable tlalocai-raspberry-agent
sudo systemctl start tlalocai-raspberry-agent
sudo journalctl -u tlalocai-raspberry-agent -f
```

## Configuration

Default configuration lives in `appsettings.json`. It includes:

- `Agent.Mode`: `Simulation` or real mode.
- `Backend.BaseUrl`: cloud backend or gateway URL.
- `Backend.ApiKey`: device API key generated by the Devices API.
- GPIO pins for tower, cistern, flow sensor and ESP32 status inputs.
- ESP32 serial ports `/dev/ttyUSB0` and `/dev/ttyUSB1`.
- Safety options for low tower level, no-flow shutdown and unsafe-command rejection.

## GPIO and serial

Recommended Raspberry BCM map:

- Tower level sensors: GPIO5, GPIO6, GPIO13, GPIO19, GPIO26.
- Cistern level sensors: GPIO12, GPIO16, GPIO20, GPIO21, GPIO25.
- Hall flow sensor: GPIO23.
- Tower pump output: GPIO17 through a power driver.
- Cistern pump output: GPIO27 through a power driver.
- ESP32 A status inputs: GPIO4, GPIO18, GPIO22, GPIO24.
- ESP32 B status inputs: GPIO10, GPIO9, GPIO11, GPIO8.

ESP32 communication uses USB serial by default:

- ESP32 A: `/dev/ttyUSB0`
- ESP32 B: `/dev/ttyUSB1`

If UART pins are used instead of USB serial, document TX/RX wiring and common GND before deployment.

## Electrical safety

- Do not connect pumps or valves directly to GPIO.
- Use MOSFET drivers, isolated switching modules, contactors or SSR modules appropriate to the load.
- Use an external power supply for pumps and valves.
- Join Raspberry, ESP32 and actuator supply GND when using common DC switching.
- Convert any 5V sensor output to 3.3V before Raspberry or ESP32 GPIO input.
- Add flyback diodes to DC inductive loads.
- If pumps are AC, use a properly rated contactor, SSR or isolated module. Do not manipulate mains wiring without proper protection.

## Simulation mode

The default `Agent.Mode` is `Simulation`, so the worker can run without Raspberry or ESP32 hardware. The simulated backend is used when `Backend.BaseUrl` still contains `TU_BACKEND_EN_NUBE`; otherwise the simulated GPIO and ESP32 drivers will publish to the configured backend using outbound HTTP.

Simulation supports:

- Full, low and empty tower/cistern input states.
- Empty and full container states.
- Valve lock and blocked open attempts.
- Normal flow and no-flow safety through the flow pulse counter.
- Backend disconnected behavior through the offline telemetry queue.
